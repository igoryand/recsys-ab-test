# A/B Test Design — нейросетевой ранкер vs CatBoost

Проект по проектированию A/B-теста для раздела **«Что смотреть»** онлайн-кинотеатра.

**Цель:** проверить, увеличивает ли нейросетевой ранкер CTR рекомендаций по сравнению с текущим CatBoost без ухудшения ключевых guardrail-метрик.

[Подробный экспериментальный план →](./ab_test_design.ipynb)

## TL;DR

| Параметр | Значение |
|---|---|
| Эксперимент | CatBoost vs нейросетевой ранкер |
| Primary metric | CTR рекомендаций |
| Secondary metrics | глубина скролла, просмотры на пользователя, время до первого клика |
| Guardrail metrics | p95 времени загрузки, ошибки, 7-day retention, жалобы |
| MDE | +5% относительно |
| Power | 80% |
| α | 0.05 |
| Распределение | 50 / 50 |
| Длительность | 2 полных недели |
| Единица рандомизации | пользователь (`user_id`) |
| Расчётная выборка | 25 580 пользователей на группу |

## Scenario

В разделе «Что смотреть» используется бесконечная лента рекомендаций. Сейчас фильмы и сериалы ранжируются с помощью **CatBoost**.

Команда рассматривает замену ранжировщика на **нейросетевую модель**, которая потенциально лучше улавливает сложные зависимости между историей поведения пользователя, контекстом и признаками контента.

Гипотеза:

> Если заменить CatBoost на нейросетевой ранкер, CTR рекомендаций увеличится минимум на 5% относительно, поскольку новая модель лучше ранжирует релевантный контент.

При этом рост CTR не должен сопровождаться практично значимым ухудшением guardrail-метрик.

> **Важно:** baseline, MDE и дневной трафик в проекте являются сценарными допущениями. Исторические данные реального онлайн-кинотеатра не используются.

## Experiment Design

**Control (A)** — текущий ранкер на CatBoost.  
**Treatment (B)** — нейросетевой ранкер.

В эксперименте меняется только модель ранжирования. Верстка, число карточек, механика скролла и алгоритм формирования пула кандидатов остаются неизменными.

- **Единица рандомизации:** `user_id`
- **Распределение трафика:** 50 / 50
- **Целевая аудитория:** пользователи, которые заходят в раздел «Что смотреть»
- **Исключения:** боты и сотрудники компании
- **Фиксация варианта:** пользователь остаётся в одной группе на протяжении эксперимента
- **Длительность:** минимум 2 полных недели

Распределение проверяется через **SRM (Sample Ratio Mismatch)**. При значимом отклонении от ожидаемого 50/50 тест не анализируется до выяснения причины.

## Metrics

### Primary

**CTR рекомендаций**

Доля уникальных пользователей, кликнувших хотя бы на один рекомендованный объект, среди пользователей, увидевших ленту.

`CTR = users_with_click / users_with_feed_view`

CTR выбрана как основная метрика, поскольку она непосредственно отражает цель изменения ранжирования — сделать верхнюю часть рекомендаций более релевантной и побудить пользователя перейти к контенту.

### Secondary

- средняя глубина скролла;
- число просмотров на пользователя;
- время до первого клика.

Эти метрики используются для интерпретации результата, но не определяют успех эксперимента самостоятельно.

### Guardrail

- p95 времени загрузки ленты;
- доля ошибок при формировании рекомендаций;
- 7-day retention;
- число жалоб на рекомендации.

До запуска фиксируется допустимое ухудшение guardrail-метрик. Одной статистической значимости недостаточно: учитывается и практический размер эффекта.

## Statistical Plan

Основная статистическая проверка — **двухвыборочный z-тест для пропорций** для CTR, двусторонний, с:

- `α = 0.05`;
- `power = 0.80`;
- `MDE = +5%` относительно;
- 95% доверительным интервалом для разницы CTR.

Статистическая гипотеза:

- **H0:** CTR в группах A и B не различается;
- **H1:** CTR в группах A и B различается.

Для продуктового решения положительный результат должен одновременно удовлетворять заранее заданному минимальному эффекту и не нарушать guardrail.

Secondary- и guardrail-метрики используются преимущественно для интерпретации и контроля качества эксперимента.

## Sample Size

При baseline CTR = 20%, относительном MDE = 5%, `α = 0.05` и мощности 80% требуется:

- **25 580 пользователей на группу**;
- **51 160 пользователей всего**.

При сценарном трафике 200 000 уникальных пользователей раздела в день расчётная выборка набирается примерно за один день.

Однако тест проводится **2 полные недели**. Это позволяет:

- захватить несколько будничных и выходных циклов;
- проверить устойчивость эффекта;
- наблюдать технические guardrail-метрики при реальной нагрузке;
- иметь запас на технические сбои и потери данных.

После остановки теста для `7-day retention` выдерживается дополнительное **7-дневное окно дозревания**.

## Data & Logging

Для анализа необходимо логировать:

- `user_id`;
- вариант эксперимента (`A` / `B`);
- показ ленты;
- клик по карточке;
- начало просмотра;
- время загрузки ленты;
- ошибки.

Вариант эксперимента фиксируется на уровне пользователя и связывается с событиями пользователя на всём протяжении теста.

## Decision Rules

| Сценарий | Условие | Решение |
|---|---|---|
| Успех | CTR статистически значимо вырос, положительный эффект не ниже MDE, guardrail не ухудшились | Внедрение нейросетевого ранкера |
| Провал по эффекту | CTR не вырос или снизился | Сохранение CatBoost |
| Провал по guardrail | CTR вырос, но guardrail значимо и практически ухудшились | Сохранение CatBoost |
| Неопределённость | Разница CTR статистически незначима | Дополнительное исследование гипотезы |

Решение принимается по заранее определённым правилам, а не по отдельным удачным срезам данных.

## Risks & Limitations

**Методологические:** изменение пользовательского поведения после запуска, сезонность и возможное загрязнение групп.

**Технические:** SRM, потеря или задержка событий, дополнительная нагрузка из-за нейросетевой модели.

**Продуктовые:** рост CTR не гарантирует рост фактического потребления контента; новая модель может стимулировать клики без соответствующего улучшения качества рекомендаций.

**Ограничения интерпретации:** результат относится только к разделу «Что смотреть» и краткосрочному периоду эксперимента. Долгосрочное влияние на LTV или годовой retention этим тестом не оценивается.
